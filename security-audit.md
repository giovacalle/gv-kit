# Security Audit

## Scope

This report summarizes obsolete dependency and CVE risks identified in the repository metadata and generated-project templates. The most important finding is the vulnerable `cookie@0.6.0` resolution in the bundled SvelteKit template lockfile.

Reviewed artifacts:

- Root package manifest and lockfile.
- `fixtures/templates/package.json` and `fixtures/templates/bun.lock`.
- Web template manifests and package fragments.
- Backend, auth service, and users service generator package output.

## Executive summary

The only confirmed CVE-level issue found in the current dependency snapshot is `cookie@0.6.0`, resolved in `fixtures/templates/bun.lock` through `@sveltejs/kit@2.59.0`. The affected package is not declared directly by gv-kit, but it is present in the generated-project template lockfile, so newly scaffolded projects may inherit the vulnerable version.

Several generated package ranges also look stale or inconsistent with the newer web template stack. These are maintenance risks rather than confirmed CVEs from this snapshot, but they increase the chance that scaffolded projects lag behind patched Cloudflare, Hono, and tooling releases.

## Findings

### 1. `cookie@0.6.0` vulnerable to CVE-2024-47764

Severity: Medium by CNA CVSS v4.0, low in GitHub advisory display.

Status: Confirmed vulnerable transitive dependency in `fixtures/templates/bun.lock`.

Evidence:

- `fixtures/templates/bun.lock` resolves `cookie` to `cookie@0.6.0`.
- `fixtures/templates/bun.lock` resolves `@sveltejs/kit@2.59.0`.
- The locked `@sveltejs/kit@2.59.0` dependency metadata includes `cookie: ^0.6.0`.
- `@types/cookie@0.6.0` is also present, but it is a type package and is not the vulnerable runtime parser/serializer.

Advisory:

- CVE: `CVE-2024-47764`
- GHSA: `GHSA-pxg6-pf52-xh8x`
- Affected package: npm `cookie`
- Affected versions: `<0.7.0`
- Patched version: `0.7.0`
- References:
  - https://github.com/advisories/GHSA-pxg6-pf52-xh8x
  - https://nvd.nist.gov/vuln/detail/CVE-2024-47764

Risk:

The vulnerable `cookie` serializer accepts out-of-bounds characters in the cookie `name`, `path`, and `domain` fields. If application code passes untrusted input into those fields, an attacker may alter how the resulting `Set-Cookie` header is interpreted. This can lead to unexpected cookie values or altered cookie attributes.

Impact on gv-kit:

- The root gv-kit CLI does not directly declare `cookie`.
- The generated SvelteKit template lockfile does include `cookie@0.6.0`.
- Scaffolded projects that use or preserve the bundled template lockfile may inherit the vulnerable transitive dependency.
- The risk is most relevant for generated applications that serialize cookies using values influenced by user input.

Recommended remediation:

- Update the SvelteKit template dependency set and regenerate `fixtures/templates/bun.lock` so `cookie` resolves to `>=0.7.0`.
- Prefer resolving this through an upstream `@sveltejs/kit` update if available.
- If an upstream update still leaves `cookie@0.6.0`, add a generated-project package-manager override only if it is compatible with SvelteKit's dependency range and behavior.
- After dependency changes, regenerate snapshots intentionally because generator output changes affect fixtures.

Temporary mitigation:

- Do not pass user-controlled values into cookie `name`, `path`, or `domain`.
- Keep cookie names and attributes application-owned constants.

### 2. Generated Hono service packages use older Hono ranges than the shared backend package

Severity: Maintenance risk.

Status: Version drift observed.

Evidence:

- Generated shared backend package uses `hono: ^4.12.0`.
- Generated auth and users services use `hono: ^4.6.0`.
- Generated auth and users services use `@hono/zod-openapi: ^1.0.0`.

Risk:

The generated services may resolve older Hono releases than the shared backend package, depending on package-manager resolution. This creates uneven runtime behavior across generated services and can delay adoption of upstream fixes.

Recommended remediation:

- Align generated auth and users service Hono ranges with the shared backend package unless there is a compatibility reason to keep them separate.
- Review `@hono/zod-openapi` alongside Hono when updating, because route schema behavior is part of the service contract.

### 3. Generated Cloudflare Worker services use broad, older Wrangler ranges

Severity: Maintenance risk.

Status: Version drift observed.

Evidence:

- Web template declares `wrangler: ^4.85.0`.
- Auth and users service generators emit `wrangler: ^4.0.0`.
- Web template uses `@cloudflare/workers-types: ^4.20260504.0`.
- Auth, users, and backend generators emit `@cloudflare/workers-types: ^4.20251101.0`.

Risk:

Worker services generated by the CLI may lag behind the web app's Cloudflare toolchain. This can cause type differences, stale binding definitions, or missed platform fixes in scaffolded projects.

Recommended remediation:

- Align generated service `wrangler` and `@cloudflare/workers-types` ranges with the current web template baseline.
- Keep `wrangler.jsonc` contract tests in sync with any typegen changes.

### 4. Zod v3 compatibility imports remain in auth template code

Severity: Maintenance risk.

Status: Obsolete compatibility path observed.

Evidence:

- The project pins Zod v4 with a workspace override.
- Auth overlay schema template files import from `zod/v3`.

Risk:

Using `zod/v3` compatibility imports inside a Zod v4 project keeps generated auth code on an older API surface. This is not a CVE by itself, but it can make future Zod upgrades harder and may hide compatibility issues in form validation libraries.

Recommended remediation:

- Confirm whether `sveltekit-superforms` and the generated auth forms still require Zod v3 compatibility.
- If not required, migrate generated auth schemas to the primary Zod v4 import path and update snapshots.

### 5. Node service runtime helpers use older ranges

Severity: Maintenance risk.

Status: Version drift observed.

Evidence:

- Generated Node-mode auth and users services emit `@hono/node-server: ^1.13.0`.
- Generated Node-mode services emit `tsup: ^8.3.0` and `tsx: ^4.19.0`.

Risk:

These ranges may resolve to older runtime and build-tool releases in generated Docker or Node deployments. No specific CVE was confirmed from the repository snapshot, but these should be reviewed when refreshing the generated dependency matrix.

Recommended remediation:

- Review the latest compatible `@hono/node-server`, `tsx`, and `tsup` versions during the same dependency refresh as Hono.
- Keep the generated Node service packages aligned across auth and users services.

## Priority

1. Fix `cookie@0.6.0` in the generated template lockfile because it is a confirmed CVE risk.
2. Align generated Cloudflare Worker service versions with the web template baseline.
3. Align generated Hono service versions with the shared backend package.
4. Review and remove Zod v3 compatibility imports if no longer required.
5. Refresh Node service helper ranges after the Hono update.

## Notes

The root gv-kit CLI dependency set is smaller than the generated-project template dependency set. The confirmed `cookie@0.6.0` issue is in the template lockfile, so remediation should focus on generated output and fixture snapshots rather than only the root package manifest.
